# 30 分钟讲清楚这个项目

> 用途：向同事或评审完整介绍这套系统时的提纲。
> 每一段都标了时间、要讲的核心、可以引用的数字，以及**容易被抓住的地方**。
> 数字全部来自 `docs/M3-acceptance.md` 与 `docs/M4-loadtest.md`，可以当场翻出来。

| 段落 | 时长 | 一句话概括 |
|---|---|---|

## 一、问题与边界（3 min）

**要讲的核心**：这套系统的难点不在"增删改查"，在一个并发命题。

> 同一座位 + 同一天 + 同一时段，任何时刻最多只能有一条有效预约。

由此推出三个必须解决的问题：

1. **超卖**：两个人同时看到"A-01 空着"，都点了确认。
2. **数量约束**：同一个人不能同时占两个座位（这不是"唯一"，是"不超过 N"）。
3. **时间维度**：预约是"座位 × 日期 × 时段"的三元组，不是座位本身。

**主动交代边界**（这段最能体现工程判断）：

- 不做支付押金、短信推送、推荐算法 —— 与核心命题无关。
- 不做微服务、不上 MQ —— 单机能解决的问题，拆成分布式只会把问题变多。
- 时段固定成三个槽位（上午/下午/晚上），不做自由起止时间 —— 见第二节的原因。

## 二、数据模型（5 min）

**要讲的核心**：并发控制的第一道防线应该落在数据库上，而不是代码里。

5 张业务表：`sys_user` / `study_room` / `seat` / `time_slot` / `reservation`，
外加 M4 的 3 张权限表。层级只有"自习室 → 座位"两层。

三个关键决定：

**① 时段必须固定**

如果存 `start_time` / `end_time`，`9:00-11:00` 和 `10:00-12:00` 明明冲突，
两行的四个值却完全不同，唯一索引根本拦不住"重叠"。固定成槽位后，
冲突判定退化成"三个值是否相同"，数据库一个索引就能管。

**② `occupy_flag` 写 1 / NULL，不是 1 / 0**

```sql
UNIQUE KEY uk_seat_date_slot (seat_id, reserve_date, slot_id, occupy_flag)
```

利用 **MySQL 唯一索引对 NULL 不生效**：只有"占用中"（1）的行参与唯一性约束。
写成 1/0 的话，`0` 是真实值也会参与比较，等于"同一座位同一时段只能有一条取消记录"，
第二次取消直接写不进去。

**③ 冗余只冗余不会变的值**

`reservation.room_id` 可以冗余，因为座位一旦建好就不会换自习室；
`study_room.capacity` 只当"规划上限"，权威座位数永远以 `seat` 表为准 —— 存两份必然不一致。

## 三、防超卖三层（8 min，全篇重点）

**要讲的核心**：每一层都是被上一层的漏洞逼出来的，不是"多写一层更保险"。

### 第一层：唯一索引

挡住：同一座位同一时段的重复写入。**这是正确性的底线，任何情况下都不能去掉。**

挡不住两件事：
- "每人每时段最多 1 个座"是**数量约束**，唯一索引只能表达"某组值唯一"。
- "查信用分 → 查冲突 → 写单"这串操作之间有时间缝隙。

复现方式（有一个专门的脚本）：同一个用户拿着同一个 token，
同时抢**两个不同座位**（同日期同时段）—— 两单都会成功，因为唯一索引只看"座位是否重复"。

### 第二层：乐观锁

在 `sys_user` 上加 `version`，写单前做一次 CAS：版本对上才 `version + 1`。
挡住：同一用户的并发修改，也就挡住了"一人占两座"。

**这里的数字要讲出来**：20 个用户抢同一个座位，加之前 2 单全成功；
加之后 1 个 200、1 个 `1016`，回库计数 1。

**主动暴露局限**（这是一个加分点）：

> CAS 打在**整行 `sys_user`** 上，粒度比业务不变量（用户 × 日期 × 时段）粗。
> 同一个人并发预约**不同时段**也会互相撞版本号，重试 3 次用完就返回 `1016`，
> 属于假冲突。正确做法是把版本号下沉到 (user, date, slot) 维度的行或 Redis 计数，
> 当前实现是为了演示 CAS 而刻意保留的简化。

### 第三层：分布式锁

乐观锁是"检测冲突 + 重试"，冲突多了就是白白重试。锁是"排队等待"。
先手写（`SETNX` + UUID + Lua 释放 + 自旋），后换成 Redisson（看门狗自动续期）。

**关键细节：锁在外、事务在内。**

如果事务在外、锁在内，事务提交可能发生在 `unlock` 之后 ——
下一个线程拿到锁时读到的还是旧数据。所以用 `TransactionTemplate` 手动控制边界，
让 `unlock` 必然发生在提交完成之后。

**验证手法**（这个比结论更有说服力）：在"事务内、锁内"插一段 sleep 制造长耗时窗口，
窗口在锁外时返回 `1016`，把 sleep 移进事务后返回 `1015` —— 说明锁确实包住了事务。

### 三层的关系

互补，不是替代：唯一索引是底线（锁失效、代码写错都还兜得住），
锁把并发收敛（避免大量无谓重试），乐观锁补上锁之外的单机并发。
任一层被绕过，数据仍然是对的，只是失败信息会变得难懂。

## 四、缓存（5 min）

**要讲的核心**：缓存不是"加个 `@Cacheable`"，是**三件不同的事**。

| 问题 | 场景 | 手段 |
|---|---|---|
| 穿透 | 查一个根本不存在的 key，每次都打到库 | 空结果也缓存（TTL 60 秒，比正常值短） |
| 击穿 | 热点 key 过期的瞬间，大量请求同时回源 | 回源加互斥锁，只放一个线程去查 |
| 雪崩 | 大批 key 同一时刻过期 | TTL 加随机量打散 |

**一致性用 Cache Aside + 延迟双删**：写库前删一次，提交后再删一次，
500ms 后再删一次。为什么要有最后那次 —— 因为读线程可能已经把旧值读进内存，
正准备写缓存，删早了就会被它覆盖回来。

**必须主动说的局限**：

> 500ms 是个经验值，假设"绝大多数查询能在 500ms 内完成"。
> 它挡不住"查询超过 500ms 且恰好在那个窗口写缓存"的情况。
> 更稳的做法是用 binlog 订阅（Canal）或给缓存值带版本号，成本更高。

**实测数据**：同一套代码，缓存命中 3273 QPS（每请求 0.002 次库），
全回源 1402 QPS（1.04 次库）—— QPS 差 2.3 倍，数据库查询差 500 倍。

**一个真实的物证**：M3 做延时队列时发现，超时释放后数据库层已经释放了座位，
但接口查出来还是"占用"——因为那条写路径忘了失效缓存。最长要等 7 分钟（TTL）才可见。
这个 bug 是靠"造一条超时数据 + 立刻查接口"发现的，不是靠读代码。

## 五、异步与防护（4 min）

**超时释放**：ZSet 延时队列（score = 签到截止时间的毫秒值），定时任务每 30 秒轮询，
用 Lua 脚本原子地"取出并删除"。没有用 MQ，因为单机场景下 ZSet 足够，
且少一个中间件就少一处要运维的东西。

**限流**：令牌桶（Lua 实现，Hash 存 tokens / lastRefill），下单接口 10 容量、5/s。
选它不选固定窗口，是因为固定窗口在窗口边界会出现"两个窗口各打满一次"的双倍突发。

**幂等**：一次性令牌，**两个 key 分工**：

- `idempotent:issued:{token} -> userId`：签发凭证，不删 —— 证明令牌是服务端发给这个人的。
- `idempotent:token:{token}`：消费标记，业务失败才删（等于归还令牌）。

合成一个 key 的话，令牌被归还之后就分不清"这是伪造的"还是"刚被还回来的"。

## 六、工程化与局限（5 min）

**权限**：3 张表（角色 / 权限点 / 角色-权限），**没有 `sys_user_role`** ——
一个用户一个角色，`sys_user.role` 已经是唯一真相源，再加一张表就有两个真相源。
鉴权用注解 + 拦截器，注意"不标注解就放行"，所以每个接口都要逐个对过。

**报表口径**（三张报表踩过的三个坑，全是业务语义问题，SQL 都跑得通）：
1. 不能用 `occupy_flag = 1` 当"占用几个座"——终态后它被置 NULL，查历史日期全是 0。
2. 必须 `COUNT(DISTINCT seat_id)`——同一座位同时段可能先违规再被订走，`COUNT(*)` 会算两次，上座率超 100%。
3. 按 `reserve_date` 分组（业务口径），不是 `create_time`（流量口径）。

**单元测试**：10 个用例，纯 Mockito，不连 MySQL / Redis。只测"改坏了也不会报错"的规则：
签到窗口的三个时间分支、下单前的三条拦截、四条写路径都注册了缓存失效。
覆盖率只有 15%，这是刻意的 —— 测 MyBatis-Plus 的 CRUD 等于测框架。

**一键部署**：`docker compose up -d --build`，多阶段构建，配置全走环境变量，
`.env` 不进版本库。实测 2 分 16 秒构建完成，三个服务 healthy，Redis 开 AOF 重启不丢数据。

**已知局限（主动收尾，别等别人问）**：

1. 乐观锁粒度粗（第三节已说），同用户并发不同时段会假冲突。
2. 延迟双删的 500ms 是经验假设，不是数学保证。
3. 热门榜单只在 Redis，重启会丢，生产环境应定时落库。
4. 压测数据只有 1.2 万行，报表在百万行下的表现没验证。
5. 单实例、无负载均衡，所有 QPS 数字都是 Compose 单机的。
6. 还没上云服务器，公网地址暂时没有。

## 附：现场白板演练（10 分钟，提前练两遍）

按这个顺序写，每一步都先说"为什么"，再写代码：

1. **先写表**：`reservation(id, user_id, seat_id, reserve_date, slot_id, status, occupy_flag)`，
   加 `UNIQUE(seat_id, reserve_date, slot_id, occupy_flag)`。
   讲清 `occupy_flag` 为什么是 1/NULL。
2. **写下单流程**（伪代码 8 行）：校验时段 → 校验座位 → 校验信用分 → 查冲突 → insert → 返回 id。
3. **指出漏洞**：两个请求同时走到"查冲突"，都查到 0 条，然后都 insert；
   唯一索引挡住的是"同一座位"，挡不住"同一用户抢两个座位"。
4. **补乐观锁**：读 version → `UPDATE sys_user SET version = version + 1 WHERE id = ? AND version = ?` →
   影响行数为 0 就重试（最多 3 次）。
5. **收尾一句**：如果要求跨实例强一致，就再加一层 Redisson 锁，锁在外、事务在内。
