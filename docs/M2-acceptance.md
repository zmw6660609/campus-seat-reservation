# M2 核心闭环 · 验收记录

> 环境：JDK 17 / Spring Boot 3.3.13 / MyBatis-Plus 3.5.7 / MySQL 8.0.46 / Redis 5.0.14.1
> 方式：跳过测试打包，以独立实例（端口 18080）拉起，纯接口调用，不依赖 IDE
> 日期：2026-10-09

## 一、验收范围

M2 的目标是**核心业务闭环 + 并发正确性**。验收覆盖：

1. 登录注册与登录态
2. 自习室 / 座位的管理端操作
3. 「查空座 → 预约下单 → 我的预约 → 签到 → 取消 → 再查空座」全链路
4. 同一座位同一时段的高并发抢占

## 二、功能链路验收

| 步骤 | 预期 | 实际 | 结论 |
|---|---|---|---|
| 注册 / 登录 | 返回 token | 200，token 正常 | 通过 |
| 查空座 | 返回可用座位列表 | 40 个 | 通过 |
| 预约下单 | 返回新预约单 ID | 200，返回 `reservationId` | 通过 |
| 再查空座 | 该座位从列表消失 | 39 个 | 通过 |
| 我的预约 | 仅返回本人预约，按日期倒序 | 字段完整，无越权数据 | 通过 |
| 取消预约 | 状态置 4，座位释放 | 200，再查空座恢复到 40 | 通过 |
| 取消后重新预约同一座位 | 应成功 | 成功，返回新 ID | 通过 |
| 签到 | 窗口内可签到 | 200，`status=2` | 通过 |
| 签到后取消 | 应被状态校验拒绝 | 1003「预约状态非法」 | 通过 |
| 新增自习室 / 批量生成座位 | 正常落库 | 200 | 通过 |
| 座位分页 | `total` 大于 0 | `total=52` | 通过 |

**签到的窗口验证方式**：签到窗口为「时段开始前 15 分钟 ~ 时段开始 + 宽限期」，而验收下单必须使用未来日期，两者天然冲突。验收时临时将字典表中该时段的 `start_time` 调整至当前时间附近，用当天日期完成下单与签到，**验完已恢复原值**。业务代码未做任何为验收而妥协的改动。

## 三、并发验收

**目的**：验证「同一座位 + 同一天 + 同一时段只能有一条有效预约」这条核心命题。

**方法**：20 个不同账号同时抢同一个座位、同一天、同一时段。

> 注意：必须使用 20 个**不同用户**。同一个用户会被「同人同时段只能占 1 个座」的前置校验挡在门外，得到的「只成功 1 单」是假通过，无法证明唯一索引生效。

**结果分布**：

| 返回 | 数量 |
|---|---|
| `1001 该座位在该时段已被预约` | 19 |
| `200 操作成功` | 1 |

总耗时 132 ms。

**回库核实**（唯一可信的判据 —— 返回码只能说明接口挡没挡住，数据库才能说明最终状态）：

| 查询 | 结果 |
|---|---|
| `occupy_flag = 1` 的记录数 | **1** |
| 该「座位 + 日期 + 时段」的总行数 | **1** |
| `deadline` | `2026-10-12 18:20:00`（时段 18:00 开始 + 宽限 20 分钟，计算正确） |

20 个并发请求中，19 个在应用层被拦下，1 个写入成功；即便应用层的校验被绕过，`uk_seat_date_slot` 唯一索引仍会在数据库层拦下重复写入。

## 四、复现方式

### Postman

导入 `postman/CampusBook.postman_collection.json`，按目录顺序执行：

```
01 准备        健康检查 → 注册 → 登录（自动保存 token）
02 管理端      新增自习室 → 自习室列表（自动取 roomId）→ 批量生成座位 → 座位分页
03 预约闭环    查空座（自动取 seatId）→ 下单（自动保存 reservationId）
               → 我的预约 → 签到 → 取消 → 再查空座
```

`token` / `roomId` / `seatId` / `reservationId` 均由请求的 test 脚本自动串联，预约日期由 pre-request 脚本动态生成（取「今天 +2 天」），不需要手工改任何变量。

### 命令行

`_accept.sh` 可完成同一条链路，支持按参数区分取消链路与签到链路：

```bash
DATE=2026-10-11 SLOT=2 bash _accept.sh   # 取消链路
DATE=$(date +%F) SLOT=2 bash _accept.sh  # 签到链路（需先调整该时段起始时间）
```

### 并发

```bash
node _loadtest.js <tokens 文件> <seatId> <date> <slotId>
```

`tokens` 文件每行一个 token。脚本强制以**字符串**传递雪花 ID —— 19 位 ID 超出 JavaScript 安全整数范围，转为 `Number` 会丢失精度，后端将查不到该记录。

## 五、已知局限

- **校验链与写入之间存在时间缝隙。** 下单流程中「查空座 / 判信用分 / 写预约」是多步操作，并发请求可以插进任意两步之间。当前由数据库唯一索引兜底，能保证最终一致性，但被拦下的请求得到的是「该座位已被预约」而不是更精确的原因。M3 将用乐观锁与 Redis 分布式锁缩短乃至消除这个缝隙。
- 签到时间窗口的前后分钟数为固定值，尚未做成配置项。
- 座位查询未做缓存，M3 将引入多级缓存与穿透 / 击穿 / 雪崩防护。

## 六、本次验收中发现并修复的问题

| 现象 | 根因 |
|---|---|
| 下单返回 500，日志为 `Unknown column 'starttime' in 'field list'` | 实体中多出了表中不存在的列。ORM 按实体生成 SQL，不核对表结构 |
| 取消返回 200，但座位始终无法恢复 | 更新策略默认跳过 null 字段，导致释放占用的语句根本没执行 |
| 取消接口报出「该座位已被预约」这一无关错误 | 从新增接口复制时误用了插入语句，主键冲突被捕获后抛出了错误的业务码 |
