# 压测报告 · 座位预约平台

> 被测版本：`f842dca`（M4-5 完成的 Docker 部署形态）
> 压测日期：2026-10-20
> 所有数字都可以用本文第 2 节的命令重跑出来。

## 1. 结论先行

| 问题 | 答案 |
|---|---|
| 查询接口能扛多少 | **约 4700 QPS**（100 并发），越过这个点开始崩塌：200 并发时 QPS 掉回 1702、P99 冲到 2.4 秒 |
| 缓存值多少 | 命中时 **3273 QPS**，同一套代码每个请求只查 1.04 次库；回源时 **1402 QPS** —— **QPS 差 2.3 倍，数据库查询差 500 倍** |
| 写入能扛多少 | 受令牌桶限制，**112 QPS**（20 个并发用户 × 5 req/s 的理论上限 100），**瓶颈不在数据库，在限流策略** |
| 防超卖有没有守住 | 10 并发抢同一座位，5407 次请求里 **恰好 1 单成功** |
| 报表慢不慢 | 12000 行数据下，冷查询 13.7ms，命中 60 秒缓存 3.8ms |

## 2. 怎么复现

### 2.1 环境

| | 配置 |
|---|---|
| 被测机 | VMware 虚拟机，Ubuntu，**4 vCPU / 4 GB**，Docker Compose 单机（MySQL 8.0.46 + Redis 5 + 应用，三个容器） |
| 压测机 | Windows 宿主机，Node 24，**跨 VMware NAT** 访问被测机（与服务器不同机） |
| 数据量 | 60 座位 / 60 用户 / 12000 条历史预约（近 120 天，每天 100 条） |
| 连接池 | 默认 HikariCP（10 连接），Tomcat 默认 200 线程 |

> 压测机与被测机不同机、跨 NAT，所以下面所有数字都含网络往返，不是纯 CPU 上限。

### 2.2 命令

```bash
# 造数据（幂等，可重复执行）
docker compose exec -T mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" < bench/prepare.sql

# 四个场景
node bench/load.js seat-hit   20 15      # 查空座 · 缓存命中
node bench/load.js seat-miss  10 1500    # 查空座 · 每次换日期，全部回源
node bench/load.js order      20 15      # 下单 · 每人一个专属座位
node bench/load.js same-seat  10 3       # 下单 · 全部抢同一座位
```

数据库查询次数用 `SHOW GLOBAL STATUS LIKE 'Questions'` 在压测前后各取一次差值。

## 3. 结果

### 3.1 查询侧：缓存命中 vs 全部回源

| 场景 | 并发 | 请求数 | QPS | P50 | P95 | P99 | MySQL 查询数 |
|---|---|---|---|---|---|---|---|
| `seat-hit` 缓存命中 | 20 | 49,101 | **3273** | 5.4ms | 11.8ms | 17.4ms | **108** |
| `seat-miss` 全部回源 | 10 | 1,500 | **1402** | 6.6ms | 11.6ms | 16.8ms | **1563** |

换算成"每个请求查了几次库"：

- 命中：`108 / 49101 ≈ 0.002` 次（那 108 次里还包含 60 个压测用户登录时的查询）
- 回源：`1563 / 1500 ≈ 1.04` 次

**这就是 M3-5 那层 Cache Aside 的直接收益**：QPS 提高 2.3 倍，数据库压力降低约 500 倍。
如果按 3000 QPS 全回源算，MySQL 需要扛 3000 QPS 的简单查询 —— 这台 4C 机器扛不住多久。

### 3.2 查询侧的饱和点

固定 `seat-hit`，只改并发（每次 10 秒）：

| 并发 | QPS | P50 | P95 | P99 |
|---|---|---|---|---|
| 5 | 2438 | 2.0ms | 2.9ms | 3.6ms |
| 20 | 3273 | 5.4ms | 11.8ms | 17.4ms |
| 50 | 4376 | 9.7ms | 19.4ms | 27.3ms |
| 100 | **4684** | 18.8ms | 34.9ms | 49.4ms |
| 200 | **1702** | 40.1ms | 77.2ms | **2456ms** |

读法（这一段比数字本身重要）：

- **5 → 50 并发：QPS 涨了 1.8 倍，延迟只涨 4.8 倍** —— 这时系统还有余量，加并发能换吞吐。
- **50 → 100 并发：并发翻倍，QPS 只涨 7%，P99 从 27ms 涨到 49ms** —— 收益开始不抵成本。
- **100 → 200：QPS 反而是 100 并发时的 36%，P99 从 49ms 涨到 2.4 秒** —— 队列开始堆，请求在等而不是在算。

拐点在 100 附近。200 那次 P99 的 2.4 秒里几乎没有"计算"，全是排队等待（Tomcat 默认 200 个线程被占满后，
新请求进 `acceptCount` 队列，队列也满了才开始拒/等）。

### 3.3 写入侧：下单吞吐

| 指标 | 数值 |
|---|---|
| 总请求（含被限流的） | 34,792 |
| 成功下单 | **1,680**（单里 20 个用户 × 84 个可用组合，正好跑完） |
| **成功 QPS** | **112.0** |
| 成功请求延迟 | P50 26.2ms / P95 49.4ms / P99 67.9ms |
| 被限流（1017） | 33,112 |

**重点在"成功 QPS"这一列。** 令牌桶是容量 10、每用户每秒补 5 个，20 个并发用户的理论上限就是
`20 × 5 = 100 QPS`，实测 112 QPS（突发令牌贡献了一点头部）—— **对得上，说明写入侧已经被限流策略锁死，
数据库远没有到瓶颈**。

这也是这个项目最值得讲的一处设计权衡：限流是为了保护系统，代价是**它自己变成了吞吐上限**。
真要提吞吐，是把"每用户 5/s"这个策略改成按全局限流，或者按接口分级 —— 那是业务决策，不是性能优化。

### 3.4 防超卖

10 并发、3 秒，5407 次请求抢同一个座位：

| 返回码 | 次数 | 含义 |
|---|---|---|
| `200` | **1** | 抢到了 |
| `1001` | 216 | 该座位已被预约 |
| `1015` | 23 | 你在该时段已有预约（**已经成功的那个用户**继续打，撞到的是这条） |
| `1017` | 5167 | 被限流 |

回库核对：该座位该时段 `occupy_flag = 1` 的记录 **恰好 1 条**。

> 拒绝码的分布本身能说明检查顺序：限流最先（1017 最多），然后是"每人每时段 1 座"（1015），
> 最后才是"座位被占"（1001）。赢家再打会先撞 1015 —— 因为他的预约已经存在了。

### 3.5 报表接口

12000 条历史预约，`days=14` 的趋势和当天上座率：

| 调用 | 耗时 |
|---|---|
| `/admin/stats/trend?days=14` 首次（走 SQL 聚合） | 13.7ms |
| 同上，命中 60 秒缓存 | 5.3ms / 3.9ms |
| `/admin/stats/occupancy` 首次 | 9.0ms |
| 同上，命中缓存 | 5.0ms / 3.0ms |

报表是管理端接口、调用频率低，60 秒缓存的意义不是省 CPU，而是**避免多人同时打开仪表盘时反复扫全表**。
这个数据量（12k 行）还看不出聚合的代价，量级要到百万行才会显形 —— 见第 5 节。

## 4. 瓶颈：三条，每条都有证据

**① 写入的瓶颈是限流，不是数据库。**
证据：成功 QPS 112 ≈ 并发数 × 5。如果数据库是瓶颈，这个数字应该随并发变化，而不会刚好卡在
"每用户每秒 5 个令牌"上。

**② 查询的瓶颈是应用层线程，不是 MySQL。**
证据：100 并发时缓存命中路径 MySQL 几乎零查询（`0.002 次/请求`），QPS 却已经封顶 4684；
而 200 并发时 QPS 反降、P99 涨 50 倍 —— 这是排队特征，不是数据库慢查询特征。
MySQL 慢查询在压测前后都是 0（`log_slow_queries` 未开启，但 `Questions` 增速与请求量线性对应）。

**③ 缓存是这套系统里性价比最高的一次优化。**
证据：同一套代码，只改缓存命中与否，QPS 2.3 倍、数据库查询 500 倍。

## 5. 这份数据的局限（必须写清）

1. **12,000 行还压不出报表的痛点。** 报表的 `COUNT(DISTINCT)` + 分组在百万行级才会变慢，
   现在的 13.7ms 不代表真实数据量下的表现。
2. **压测机与被测机不同机，跨 NAT。** 200 并发那次 P99 的 2.4 秒里混着客户端排队，
   不能全部算在服务端头上。要更干净的数据，应该用 `wrk`/`JMeter` 在被测机本地打。
3. **只跑了 10~15 秒的短时压测**，没有验证长时间运行下的内存、连接池、Redis 增长。
4. **`docker stats` 的 CPU 占用没采到**（需要在客机内执行）。当前对饱和点的判断基于
   "QPS-并发-延迟"曲线的形状，而不是 CPU 数字。
5. **单实例、无负载均衡。** 这是 Compose 单机的结果，不是集群能力。
